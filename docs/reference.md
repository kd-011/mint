# Mint engineering notes

Notes on the code in this repository: the engine, the API, the screens and the design system. Start with the top-level `README.md`. The assistant, where it appears below, is the maintainer's own private AI assistant. The integration is optional and off unless `MINT_CHAT_KEY` is set. Some sections describe one particular deployment. Treat those as one worked example. Mint pulls bank accounts through the Redbark API (Australian CDR) and keeps its own full copy, since Redbark stores nothing. It also takes accounts Redbark cannot see by hand, in any currency, with CSV statement import. It categorises, matches transfers, budgets, tracks tax and business spend, and raises alerts.

## Stack

Zero-dependency Node 22 ESM: `node:http` + `node:sqlite`, vanilla JS SPA in `public/`, no npm packages, no build step. Money is integer cents, dates DD/MM/YYYY, timezone `MINT_TZ` (default Australia/Perth; see Timezone in docs/self-hosting.md).

- `server.mjs`: HTTP server, gate check, API, scheduler, static shell (asset version hashed from `public/`)
- `lib/redbark.mjs`: Redbark v2 client (version header, token pagination, 5,000-row window splitting, Retry-After, from_too_old guard)
- `lib/ingest.mjs`: backfill, 30 min poll, nightly reconcile, balance snapshots, pending to posted
- `lib/accountmerge.mjs`, `scripts/merge-accounts.mjs`: one real bank account under two Redbark ids (a bank re-linked as a second connection issues new ids and often a new name; the old ids stay listed) is folded into one row. A rename alone keeps the id and just updates the name in `syncMeta`. The sync only reports a pair (a log line after each sweep); merging is a person's step: `node scripts/merge-accounts.mjs` is a dry run on a copy (counts only), `--apply` snapshots to `backups/` first, `--undo <id>` restores everything and the pair is never merged again, `--list` shows the history. Match = institution + masked number + currency + type, across different connections only, never the name; manual accounts never match. The newest row on an active connection survives. The older row is marked `merged_into` and `status = 'gone'` (never deleted, and `syncMeta` leaves it retired); its transactions, balance days, rules, income sources, pay plan lines, goals and loan inputs move to the survivor, and the owner's nickname, business, hidden, spendable and order carry over. A transaction that is the same date, amount and description as one the survivor holds is neither moved nor deleted: it stays on the retired row (its category, note, business flag, receipts, tax tag, owed payments and transfer pairs are carried or re-pointed to the surviving copy, all undoable), and every query that scans or totals transactions skips rows whose account has `merged_into` set (`lib/live.mjs` `LIVE()` for queries on transactions alone, `AND a.merged_into IS NULL` on the accounts join elsewhere: spend, income, tax, transfers, categorise, cycles, forecast, plan, bills, debt, reports, search).
- `lib/webhook.mjs`: HMAC verification for both Redbark signing formats, delivery dedupe
- `lib/db.mjs`: schema (accounts, transactions, balance snapshots, manual assets, categories, rules, budgets, tax tags, receipts, transfers, alerts, sync log, goals, owed and owed_payments, fx_rates, manual_imports)
- Manual accounts: `lib/manual.mjs` (accounts and rows kept by hand, any currency, balance and snapshot rebuild), `lib/fx.mjs` (Frankfurter client and the daily rate cache, shared with the share prices), `lib/csvimport.mjs` (CSV parser, mapper, preview, idempotent import, undo), `public/manual.js` (the screens). See "Manual accounts and other currencies" below
- `lib/merchant.mjs`: merchant from the description (card, EFTPOS, facilitator and BNPL noise stripped) and a grouping key
- `lib/categories.mjs`: seed category set, provider_category fallback map, seed rules
- `lib/categorise.mjs`: rules (retroactive), manual picks with "always", the capped and cached model pass
- `lib/logos.mjs`: merchant logos. Merchant to domain (built-in AU map, a domain in the text, one model question per merchant), icon from Google s2 then DuckDuckGo fetched server side behind an SSRF guard, cached in `merchant_logo`, served at `GET /api/logo/<merchant key>`; `PUT` sets or clears a domain by hand. The page only gets a `logo` URL when one is cached. Bank logos use the same pipeline: `INSTITUTION_DOMAINS` (Bankwest, ANZ, NAB and the other common AU banks, matched loosely on the institution name) gives a domain, `runBanks` fetches the 256px favicon first (then the usual sources) and caches it under `bank:<institution slug>` (a key a merchant key can never equal), `/api/accounts` carries `logo` per account (`withBankLogos`), served at `GET /api/logo/bank%3A<slug>`. It runs 2 s after boot and at the start of every logo pass (so after every sync); a bank not in the map has no row and keeps its letter tile. `BUNDLED_BANK_ICONS` ships a cleaned icon for a bank whose own is not fit to show: NAB's app icon (what Google and nab.com.au both serve) has a grey "www" ribbon baked into its corner, so `lib/bank-icons/nab.png` (ribbon painted out, a little margin) is put in instead of fetching and replaces a copy fetched earlier (an etag check, so it happens once; the `merchant_logo.source` CHECK has no room for a new value, it stays `map`). Bank tiles (`logoTile({ bank: true })`, class `bk`) are fitted by `wireLogoTiles`: a canvas sample of the four corners says full-bleed (Bankwest, NAB: fills the tile) or a bare mark (ANZ: inset 7px on the neutral tile). The logo image class is `lgi`; it used to be `lg`, which is also the chart legend pill (min-height 44px) and stretched every logo.
- `lib/search.mjs`, `lib/insights.mjs`, `lib/views.mjs`: global search, what changed this pay cycle, saved Transactions views (see Everyday features below)

See "Pay cycles and the money plan" below

Add a script to `SCRIPTS` in `server.mjs` and it is listed in the page and the worker

## Run

- Run it as any long-lived service (the maintainer uses a systemd user unit, `mint.service`), port `MINT_PORT=8970`, binds 127.0.0.1.
- `.env` (chmod 600, gitignored), see `.env.example`. `REDBARK_API_KEY` is optional: unset, the server logs `bank feed is off` once at start-up, `lib/ingest.mjs` is built with no client (a poll, reconcile or snapshot does nothing and writes no sync log row; Wise still runs when its token is set), the scheduler tick returns early, `POST /api/sync` answers 409, and `/api/accounts` carries `sync.redbark: false` so the page hides the Sync tile, the sync card and every Redbark prompt (see `docs/csv-import.md`).
- Exposure: a reverse proxy with a forward-auth login in front of `127.0.0.1:8970` (see the top-level README). The app also requires the gateway's `Remote-User` header (`MINT_USER`) and its shared secret `X-Mint-Gate` (`MINT_GATE_KEY`, 32+ characters, constant-time compare) on every route except the PWA install assets, `/healthz`, `/api/redbark/webhook` and the loopback bearer door. The proxy adds the header from its own copy of the key; the two copies must match, so rotate both and restart both. Once a key has been used (setting `gate_key_enabled_at`), the server refuses to start without one; delete that setting to turn the gate key off on purpose.
- Fingerprint lock: see [Fingerprint lock](#fingerprint-lock). On by default; every data route also needs the unlock cookie.
- Webhook: the login gateway must bypass only `^/api/redbark/webhook$`. Mint checks the HMAC (5 minute replay window) before parsing the body, dedupes on the delivery or event id, and answers 503 until `REDBARK_WEBHOOK_SECRET` or `REDBARK_EVENTS_SECRET` is set. A delivery only triggers an API sync of the named accounts; rows always come from the v2 API.
- Schedule (in process): poll every 30 min (the first run backfills each account up to about 7 years), reconcile at 02:40 in the `MINT_TZ` zone, once per local day (`lib/schedule.mjs`; on a daylight saving day that skips 02:40 it runs when the clock passes it) (120 day re-walk, balances and loan details into the daily snapshot).
- Backup: a daily timer runs `scripts/backup.mjs`. Local `backups/mint-<date>.db` snapshots stay plain (this box only). With `MINT_BACKUP_HOST` set, everything off box is age encrypted to `MINT_BACKUP_AGE_RECIPIENT` (public key, in `.env`): `mint-<date>.db.gz.age`, keep 14, and `receipts-age/<file>.age`, each receipt encrypted once. No valid recipient, no off-box copy. The private key (default `~/.secrets/mint-backup-age.key`, mode 600, never committed or printed) must also be stored somewhere else safe: without it the off-box copies cannot be read. Restore test: `node scripts/restore-test.mjs` (`MINT_BACKUP_AGE_KEY` overrides the key path): decrypt, integrity, row counts, receipts count and one receipt byte for byte.

## Engine

After every poll or reconcile: the loan drawdown rule, the AU merchant rules, rules, then transfer matching, then the income pass and the one-off v2 seeds (income streams, starter budgets, pay split, Emergency Fund goal), then alerts, then the model pass in the background (income and alerts run again if it changed anything).

- Categorising precedence: manual, rule (lowest priority number, newest on a tie), the model's cached answer per merchant, Redbark's provider_category. Rule edits re-run over all history. A manual pick with `always` makes a correction rule on the merchant.
- Model: OpenRouter (`OPENROUTER_API_KEY`, `MINT_AI_MODEL`, default `google/gemini-3.1-flash-lite`). Sends merchant and description only, with account numbers, card masks and long references replaced by `#`; never amounts, balances or account ids. One question per merchant, ever (`ai_cache`), batches of 40, `MINT_AI_DAILY_CAP` merchants a day (default 1500), token use per day in `ai_usage`. A failed call backs off 2 hours.
- Transfers: same amount out and in across two of the owner's accounts within 4 days, scored on provider_category (TRANSFER_*, LOAN_PAYMENTS), a shared bank reference and the gap. Clear pairs link, doubtful ones wait in review. Across a currency (a Wise balance, `lib/transfers.mjs` `crossScore`) an AUD leg pairs with a foreign manual row when their AUD values are within 2% of the larger (the fee and the rate day), and only with Wise evidence on the AUD row (Wise wording in its description or reference, or the row on a Wise account); the foreign side being a Wise balance is not evidence, since every card purchase on it is on one. With that evidence the bank's transfer flag links the pair automatically and without the flag it goes to review; with none there is no pair. Linking one by hand allows 5%. The doubtful-transfer card shows each leg's own amount when the two differ. Linked legs and transfer-kind categories never count as spend or income. Money into a loan account links whatever the bank called the debit (the settlement deposit paid from the offset is labelled a bank fee). A leg carrying the owner's own name in transfer wording ("MS JANE QUINN C ... CREDIT TO ACCOUNT", which the bank files as income) counts as the bank calling it a transfer; wages, tax refunds and a row the owner pinned as income (`income_manual`) never do. The name comes from the salary description (`lib/owner.mjs`).
- Loan drawdowns: a seeded rule per loan account (`LOAN DRAWDOWN`, starts, priority 20, made once per account, stays deleted if the owner deletes it) files drawdowns under `Loan drawdown`, a transfer-kind category, so a settlement or construction progress claim is never spend.
- AU merchant seed rules (`seedMerchantRules`, a versioned migration, `settings.au_merchant_rules`): fuel brands (BP, Shell, Reddy Express, Ampol, Caltex, 7-Eleven, United, Puma Energy, Liberty Oil, Vibe, EG Group, Better Choice) to `Fuel` (Transport group), Woolworths, Coles and IGA to `Groceries`, Telstra and Exetel to `Phone and internet`, Uber rides to `Rideshare and taxis` (Uber Eats stays food). Source `seed`, priority 150 (after the owner's own rules, ahead of the base seeds at 200), money out only, skipped when the owner already has a rule with the same field, match and pattern, and a deleted one stays deleted. A new list bumps `MERCHANT_RULES_VERSION`. `node scripts/dry-run.mjs` prints rows matched and moved per rule on a throwaway copy.
- Recurring (`lib/recurring.mjs`): a merchant charging a steady amount on a steady cadence is a subscription, or a bill when its category is one (Home group, Rego, Government and fees, Insurance, Utilities, Phone and internet). A merchant whose rows are mostly filed under Subscriptions gets a looser second test when the strict one finds nothing: each price point is its own series, amounts within about 35% of their median, two charges are enough for monthly or longer, a stray top-up after the last regular charge is ignored, and Play Store names cut short or with a "Google" prefix are one service. Transfers, person-to-person online payments, loan instalments and everyday spend that repeats (eating out, fuel, parking, travel, debt repayments) are never subscriptions. Outside Subscriptions nothing changed, and inside it a rhythm is still needed (at least two charges a plausible cadence apart). One-off or bursty usage billing (OpenRouter, Vercel) is not guessed at: those show under "Maybe" or go in by hand.
- Subscriptions (`lib/subscriptions.mjs`, table `subscriptions`): `GET /api/subscriptions` answers `{ as_of, active, cancelled, stopped, dismissed, maybe, totals: { active_per_month, cancelled_saved_per_month } }`. Detected ones are active until the owner cancels them (`PUT /api/subscriptions/detected/:merchantKey { status: 'cancelled', cancelled_on? }`, the date defaults to today and cannot be in the future) or sets them aside (`status: 'dismissed'`); `DELETE` on the same path puts them back. Manual ones (`POST /api/subscriptions { name, amount, cadence, next_date, merchant_key?, category_id?, note? }`, `PATCH|DELETE /api/subscriptions/:id`, `status` active or cancelled) roll their next date forward by the cadence; one linked to a `merchant_key` stands in for the detected one. `detectRecurring` is what the money maths reads: cancelled and dismissed merchants are gone from the bills calendar, safe to spend, the forecast and the new-subscription alerts (a cancelled merchant also stays out of the forecast's baseline spend), manual active ones are in. `per_month` is weekly x 52/12, fortnightly x 26/12, quarterly / 3, yearly / 12. `GET /api/assistant/subscriptions` is the read-only copy for the assistant.
- Budget category view: `GET /api/budgets/:categoryId/transactions?cycle=YYYY-MM-DD` (the cycle holding that date; the current one by default) or `?month=YYYY-MM`, `include_business=1` as on the budget. Answers `{ category, basis, cycle, month, from, to, budget (the budget row or null), net, spent, count, truncated, items }`; `items` are transaction rows as `/api/transactions` returns them, newest first, up to 500. They are the rows the budget's spent figure counts (refunds and reimbursements netted, linked transfer legs and business spend left out), so they add up to it; `spent` is `net` floored at zero, as the budget counts it.
- Alerts (`alerts` table, `pushed_at` set when the assistant has delivered one): `unusual`, `subscription` (new, price rise), `sync` (account error, stale, connection, consent expiring), `budget` (90, over; once per category per pay cycle, per calendar month while there is no pay cycle), `pace` (from the cycle midpoint, flexible spend projected over 110% of the flexible budget; once per cycle), `payday` (in-app only, never pushed: the salary landed and the planned split, once per salary deposit, only within 3 days of it). A starter budget made mid-cycle does not alert (budget or pace) until the next cycle.

API (all behind the gate): `/api/transactions[/:id[/tax|/receipts]]` (filters: `q account category from to business tax direction source`), `/api/transactions/bulk`, `/api/transactions/export.csv`, `/api/search`, `/api/insights/cycle`, `/api/views[/:id]`, `/api/receipts/:id`, `/api/categories`, `/api/rules[/preview|/:id]`, `/api/categorise/status|run`, `/api/transfers[/:id[/confirm|/reject]]`, `/api/recurring`, `/api/subscriptions[/:id]`, `/api/subscriptions/detected/:merchantKey`, `/api/budgets[/:categoryId[/transactions]]`, `/api/tax/categories|summary|deductions|export.csv`, `/api/networth[/history]`, `PUT /api/home/order`, `/api/assets[/:id[/snapshots[/:date]]]`, `/api/savings`, `/api/super`, `/api/homeloan[/:accountId/inputs]`, `/api/reports/monthly|merchants`, `/api/review`, `/api/alerts[/:id/dismiss]`, `/api/summary/weekly`.

## Pay cycles and the money plan (v2)

All money is integer cents, dates `YYYY-MM-DD` in the API (the UI shows DD/MM/YYYY), local time in the `MINT_TZ` zone (default Australia/Perth). Mint never moves money: it plans, checks and nudges.

- Income streams (`income_sources`): every positive row that counts (not a transfer leg, not in a transfer or spending category, so refunds stay refunds) is `salary`, `regular`, `reimbursement` or `other`. The first matching stream by priority wins, nothing matching is `other`. A stream matches on description or merchant (`contains`, `starts`, `exact`, `regex`, or `person`, a person-to-person heuristic that skips the owner's own name, gifts, cards and loans), optionally one account and an amount band. Seeded once from the book: `SALARY/WAGES` into any account is the salary that anchors the cycle (the pay account is wherever the latest one landed); the same payer paying near the same amount ($500 or more) 10 to 18 days apart, still paying, is a regular payer on its own observed rhythm, and a projected payment counts as expected until 3 days late, then it is missed; credits that look like a person, up to $500, are "Friends paying back". The owner can pin one row (`income_manual`).
- Income is salary plus regular payers only. Reimbursements count against the spending category they pay back (from the note: dinner is Eating out, a trip is Travel, rent is Rent; else the `Reimbursements` category) and net off spend everywhere spend is counted (budgets, Reports, the assistant spend), never income. Other money in (gifts, interest, cashback, own money from elsewhere) is shown apart. In SQL, `lib/spend.mjs` joins `c` on the category a row counts against (`COUNT_CAT`).
- Pay cycles: from a salary deposit to the day before the next (deposits within 3 days are one payday). The open cycle ends the day before the predicted payday (last pay + the salary stream's cadence, 14 days), stretches while pay is late and is flagged `late` from 2 days past. A missed pay makes one long cycle.
- Budgets: `cycle_target` per pay cycle is the target; `monthly_target` stays as the monthly roll-up (cycle x 26 / 12) and old monthly rows converted x 12 / 26. `fixed` (bills, subscriptions) vs flexible. Rollover per cycle. Starter budgets: once, into an empty budgets table, after two cycles have closed, from the last six complete cycles: flexible categories take the median per-cycle spend, fixed ones the mean, single charges of $2,000 or more skipped (unless the category is a bill by nature), under $20 a cycle ($5 fixed) skipped, rounded up to the next $10 ($50 from $500), source `starter`. Home loan: a repayment into a loan account counts as spend under its own `Home loan` category (Home group, fixed). Both legs of the transfer stay Transfers, so nothing about matching, net worth or the forecast changes; budgets, the monthly roll-up, Reports and the assistant `mint_spend` read count the repayment once, as the outgoing leg of a matched `loan_repayment` pair, or as the loan-account credit when no outgoing leg is matched (a pair waiting in review counts as neither). The week around the loan's start (settlement, the borrower's own funds) is not a repayment, as in `loanFacts`. A loan drawdown (Loan drawdown) and the interest debit never count as Home loan, and card repayments stay transfers. Safe to spend and the forecast keep leaving it out, since the bills calendar already carries the instalment. The line's budget is made once (`lib/loanbudget.mjs`, after the starter pass): the repayment Mint knows (`loanFacts`) as a monthly figure, scaled to the cycle like other monthly bills, fixed, no rollover, source `starter`; delete it and it stays gone. The `spend.mjs` fragments are `SPEND_FROM`, `SPEND_COUNTS` and `SPEND_AMT`.
- Safe to spend = expected cycle income - planned savings split (plan lines that are not `spending`) - fixed bills in the cycle, paid or due (bills calendar) - flexible spend so far (all personal spend in the cycle less the bills already counted). Per day = safe / days left including today. Cash check: spendable accounts (`accounts.spendable`, else transaction accounts not named offset, emergency, saving, invest or business) less bills still due before payday.
- Pay split moves follow pass-through accounts: a transfer out of the pay account into an account that sends money on within 2 days (pay to an everyday account, straight on to the card) counts for where the money ended up. Only what was sent on moves, the rest stays with the account in the middle, each onward transfer carries no more than it was sent, and an account already on the path ends it. Split status, the suggested plan, the forecast and the assistant cycle read all use it.
- Loan: rate from the details, repayment = what the owner actually pays, always an amount he paid: the middle of the last three repayments into the loan, or the latest with fewer than three (the week around the loan start left out); the bank's figure sits beside it (its minimum instalment if it sends one, else for interest only the last interest charge). The next instalment is paid when a repayment landed after the instalment before it, up to its date, offset from the net worth mapping. Payoff compounds monthly; an extra amount per cycle counts as x 26 / 12 a month. Interest only (or under the interest), the extra is compared with the principal and interest repayment that clears it by the loan end date. Card: the PURCHASE rate from the details if there is one, else "rate unknown" and the maths leaves interest out; no statement or due date (Redbark gives none).

## Manual accounts and other currencies

Accounts Redbark cannot see (Wise, an overseas bank, a travel card) are added by hand, in any currency Frankfurter (ECB) publishes, with a balance and transactions typed in or imported from CSV.

- The rule that keeps every AUD figure honest: columns that existed before keep meaning AUD cents. A manual row's `transactions.amount` is its AUD value at the rate for its date, with the native amount in `amount_native` and the rate used in `fx_rate` and `fx_date`. An account's `balance_current` is its native balance at the latest rate, with the native figure in `balance_native`. So spend, budgets, income, tax, safe to spend, net worth and the assistant read AUD with no change, and a 100,000 THB balance counts as about $4,500 in net worth and as nothing anywhere else (`test/multicurrency-aggregates.test.mjs`). Spending on a foreign account does count, at its AUD value. Native amounts are hundredths of the unit whatever the currency's decimals (JPY too). Synced rows have `amount_native` null.
- Accounts: `accounts.manual = 1`, ids `man_` plus 16 hex, rows `mtx_` plus 16 hex (the page picks both, so a replayed offline write is harmless). Types are transaction, savings, credit-card and loan. The balance is `opening_balance` (as at the start of `opening_date`) plus every row from that date on; older rows are history inside the opening balance. Each write rebuilds the account's `balance_snapshots` (one per day something changed, each at that day's rate, native in `snapshots.native`), so net worth history works; the quote tick adds today's row once a local day. Archive sets `status = 'gone'` (out of net worth, history kept); delete takes only the account's own rows, after a confirm that shows the count, with the usual 5 second undo. Set balance records the difference as a row in `Balance adjustment` (a transfer-kind category, never spend or income).
- Sync leaves them alone: `lib/ingest.mjs` never sends a manual account to Redbark, never marks one gone; no sync, staleness or connection alert; the assistant's last-synced figure skips them. Safe to spend's cash check counts one only when the owner pins it spendable. Transfer matching skips manual accounts in another currency (an equal AUD pair there is chance); manual AUD accounts pair as usual. New rows go through the rules, the merchant derivation and the model pass like synced ones.
- Rates (`lib/fx.mjs`, table `fx_rates (currency, date, rate, source, fetched_at)`, AUD per unit by ECB date): a date takes the nearest earlier rate. A write that needs dates the cache does not cover makes one open-ended range call (`/v1/<from>..?base=CUR&symbols=AUD`), so an import of any size costs one request. Every 6 hours the latest rate for each currency a live manual account uses is fetched. Offline, the last known rate stands in and the account shows "Rate from <date>" once it is over 4 days old; new rates re-convert rows that were saved on a stand-in. With no rate at all for a date the write is refused with a 422 and nothing is saved: Mint never invents a rate. The currency list is Frankfurter's `/currencies`, cached a week. `MINT_FX_BASE` points the client elsewhere (tests). The share prices' USD rate uses the same client.
- CSV import (`lib/csvimport.mjs`): the page sends the file's bytes as base64; the server decodes UTF-8 (else Windows-1252), refuses binary, caps 2 MB and 20,000 rows, sniffs the delimiter (comma, semicolon, tab, pipe), finds the header past any bank preamble, guesses the mapping (date, description, amount or out and in columns, optional balance and reference), guesses the date order (day first by default, ambiguity reported), and parses amounts with either thousands separator, brackets, trailing minus, DR and CR. `dry_run` answers counts (import, already there, failed with row number and reason), the first rows, the warnings and the balance before and after, writing nothing. The import is one transaction and one `manual_imports` row; `DELETE /api/manual/imports/:id` removes exactly its rows. Re-importing is idempotent: `import_hash` is account, date, amount, description (case and spacing ignored) and the row's occurrence in the file, unique per account. The mapping and date order are remembered per account (`accounts.csv_mapping`) and reused for a file with the same header. `set_balance` adds an adjustment so the balance matches the statement's closing balance. Cells are stored as text; formula-looking ones stay text and are escaped on screen and quoted in the export.

### Wise sync (read only)

Set `WISE_API_TOKEN` in `.env` (a Wise personal API token) and Mint keeps a manual account per Wise currency balance current. Unset, Wise sync is silently off: no calls, no alerts. The value is read once into the client closure in `lib/wise.mjs`, sent only to `https://api.wise.com` (the base is pinned, redirects refused), and never put in an error, a log row, a setting or a response. A value saved in `.env` with surrounding quotes is accepted. The client issues GET requests only: profiles, balances and statements, so it cannot quote, transfer or change anything.

- Accounts: each STANDARD balance becomes a manual account (institution Wise, name `Wise AUD`, type transaction), found again by Wise's balance id (`accounts.wise_balance_id`, unique), so a re-sync never adds a second. A currency that is zero and has no history in the last 12 months gets no account until it holds money. Archive an account and sync leaves it alone; delete it and the next sync brings it back.
- Rows: the first run backfills 12 months in one statement call (longer ranges are walked in windows under Wise's 469 day cap) and takes the opening balance from Wise's own statement, so a clean account needs no adjustment. Later runs re-read the last 21 days (120 on the nightly reconcile, wider after an outage). Rows go through the manual insert path: local dates, native amount in `amount_native`, AUD at the rate for the row date (a missing rate refuses that account, never an invented one), rules, merchant derivation and the model pass. They are idempotent on Wise's transaction reference (`import_hash`) and each run's rows are one `manual_imports` entry (`Wise sync`), so it undoes as one.
- Balance: after the rows, the balance is set to the figure Wise reports with the usual Balance adjustment row (note "Matches the balance Wise reports"), never spend or income.
- SCA: if Wise refuses statements for strong customer authentication (403 with `x-2fa-approval`), the account runs on balances alone (`wise_statements = 'sca'`), the sheet says "Balance syncs from Wise; transactions via CSV import", and rows come from Import CSV. If even balances are refused the run fails with the exact status and a hint to check the token's scope. Nothing here works around SCA.
- Schedule: a poll (every 30 minutes) and the nightly reconcile run Wise after Redbark, on the same queue and running guard as Sync now; a webhook-scoped poll skips it. `POST /api/wise/sync` runs Wise alone (the Retry button), `GET /api/wise/status` returns `{ enabled, ok_at, error }`, and `/api/accounts` carries the same as `sync.wise` and `wise`, `wise_statements` per account.
- Failure: one `sync_log` row per run (kind `wise`). A failing currency shows its error under that account with a Retry; a run that cannot reach Wise shows on the sync card and raises one "Wise sync failing" alert per incident, and a failing or stale Wise account alerts like a bank account. Only when the token is set.

## In-app chat

A floating button on every tab opens a bottom sheet (phones) or a right-hand panel (desktop). The browser talks only to Mint, behind the sign-in; Mint calls the assistant (`POST /api/mint/chat` on `MINT_CHAT_URL`, default `http://127.0.0.1:3000`, loopback only) with `MINT_CHAT_KEY` from `.env`, which never reaches the page. It is not `MINT_API_KEY`, which opens `/api/assistant/` the other way round.

- `POST /api/chat` `{ conversation_id, message, request_id? }` streams the assistant's events through as they arrive (`start`, `tool`, `delta`, `undo`, `confirm`, `undone`, then `done` or `error`). The assistant's refusals come back as JSON `{ ok: false, code, error }` with its status (409 busy, 423 paused, 429 daily-limit or quota); a 401 or 403 from the assistant is Mint's setup fault and becomes a 502 `assistant-rejected`, never a sign-out; the assistant down is a 502 `unreachable`; no key is a 503 `not-configured`. Rate limited to 30 messages per 10 minutes (429 `rate-limited` with `Retry-After`). Message bodies and replies are never logged.
- `POST /api/chat/undo/:token` and `/api/chat/confirm/:token` are the page's way to the same tokens the bearer door issues (same operations as `/api/assistant/undo` and `/confirm`, behind the sign-in, 120 a window).
- The conversation id and history live in the browser's localStorage (last 60 messages), so it survives a refresh; Clear asks first and starts a new assistant conversation. Offline the composer is disabled with a reason, nothing is queued.
- Retry is safe. The page gives each question a `request_id` (kept on the saved message, the same on every attempt). `lib/chatturn.mjs` journals the safe writes the assistant makes through the door while that question is in flight (or up to 5 minutes after its stream ended; two different questions in flight at once are not attributed) in `chat_turn_writes`; when the same question comes back and the assistant makes the same write (same op and params, matched in order), Mint answers with the first result, same undo token, `replayed: true`, and writes nothing. A write whose undo was used since is applied afresh. Rows last as long as the undo window (24 hours). A broken reply that made a change stays on screen with its Undo ("The connection dropped here"); the resend's reply shows a replayed change as a note, not a second card. No `request_id` means no tracking, as before.
- Messages queued while a reply streams are saved with the chat. They go one at a time, in order, when a turn ends done or stopped, on page load, and when the connection returns, unless the last reply failed in a way a resend would not fix (daily limit, paused, signed out), which holds them with the reason shown.

## The assistant door

The assistant's chat tools (`mint_summary`, `mint_spend`, `mint_transactions`, `mint_budgets`, `mint_tax`, `mint_balances`, `mint_alerts`, `mint_rule_add`, `mint_tax_tag`) call Mint server to server on loopback with `Authorization: Bearer <MINT_API_KEY>`.

- The key (`MINT_API_KEY` in `.env`, 32 characters or more, the server refuses a shorter one; unset means the door is shut) opens `/api/assistant/` and nothing else, and only for a caller that connected straight to :8970 from this machine. A key presented with proxy headers (`X-Forwarded-For`, `CF-Connecting-IP`, `Remote-User`, `X-Mint-Gate`) is refused like a wrong one. Bad keys count against the same per-IP limit as bad webhook signatures. It never goes through the gate, so no Authelia bypass exists for it.
- Reads: `GET /api/assistant/owed` (the `/api/owed` answer: total, overdue, people, debts with repayments), `GET /api/assistant/summary|spend|transactions|budgets|tax|balances|alerts|categories|summary/weekly`. ## Fingerprint lock

The estate sign-in lasts up to 90 days, so on top of it Mint asks for a fingerprint (a WebAuthn passkey, user verification required, platform authenticator) every time it opens. The server enforces the lock.

- Enforcement (`server.mjs`): with the gate identity but no valid unlock cookie, every `/api/` route answers `423 {"error":"locked"}` and logs `refused ... locked`. Exempt: the lock's own `GET /api/lock/status` and `POST /api/lock/challenge|verify|register-challenge|register-verify|lock`, the open set (PWA assets, `/healthz`, `/api/redbark/webhook`), and the shell and its scripts (`index.html` and the bundles hold no data). The assistant's loopback bearer door (`/api/assistant/` with `MINT_API_KEY`) is untouched, so the `mint_*` tools and the chat's undo and confirm through the assistant keep working. The page's `/api/chat/undo|confirm` route is behind the lock like any other.
- Verification (`lib/lock.mjs`, node:crypto only, no dependencies): registration with attestation `none`, ES256 (-7) and RS256 (-257); the attestation object's CBOR, authenticator data and COSE key are parsed here and the key stored as SPKI in `lock_credentials` with its signature counter. An assertion needs a live challenge (single use, 2 minutes, in memory), `type` `webauthn.get`, origin `MINT_ORIGIN` (default `https://mint.example.com`), `rpIdHash = sha256(mint.example.com)`, both UP and UV flags, a good signature over `authData || sha256(clientDataJSON)`, and a counter that went up once the authenticator counts (passkeys that always send 0 are fine). `MINT_LOCK_DEV_ORIGIN=http://localhost:<port>` adds a localhost origin with rp id `localhost`, for tests and a throwaway check only.
- Sessions: a good assertion sets `__Host-mint-unlock` (HttpOnly, Secure, SameSite=Strict, host only): a random id plus its HMAC under `lock_cookie_secret` (random, in the settings table). The id is held hashed in `lock_sessions`, so Lock now, removing a fingerprint and a reset end it at once. 15 minutes idle (sliding on any request, and the page pings while you are reading) and 8 hours absolute. Failed checks: 20 per IP per 10 minutes, then 429. Refusals are logged with the reason and IP, never the challenge, credential id or signature.
- First run: nothing enrolled, so the lock screen offers Set up fingerprint, reachable only through the gate identity like everything else. Enrolling turns the lock on (`lock_enabled_at`) and unlocks. Any further fingerprint needs an unlocked session (Settings, Add a fingerprint). Settings lists them with Remove (the last one cannot be removed from the web) and Lock now; the header has a lock button too.
- Page (`public/lock.js`, `public/lockset.js`): the cover is in `index.html` from the first paint, so nothing behind it shows before the check. It auto-prompts once on open, shows the real browser error inline with Try again, and locks again after 15 minutes without a touch, after a minute in the background, on Lock now, and on any 423. The SPA stays mounted underneath and every `/api/` fetch waits behind the lock and is sent again after the fingerprint, so a half-typed form survives and a write made while locked lands after unlock (offline writes still queue as before). Offline, the device's own fingerprint check opens the copy saved on this device; the first call that reaches the server locks again. The service worker never caches `/api/` (merchant logo images aside, as before). Known limit: the offline copy in localStorage and the logo cache stay on the device while locked, as they did before the lock.
- No off switch in the environment once enrolled: `MINT_LOCK=off` is honoured only until the first fingerprint; after that the server refuses to start with it (same pattern as `gate_key_enabled_at`). A blank or missing flag means on.
- Lost phone, break glass (needs a shell on this box): `node scripts/lock-reset.mjs` shows what is enrolled; `--yes` deletes every fingerprint and session and rotates the cookie secret, the lock stays on and the next open offers set up; `--yes --disable` also forgets `lock_enabled_at` so `MINT_LOCK=off` is honoured on the next start. Safe with the service running.

## Timezone (`MINT_TZ`)

- `MINT_TZ` is one IANA zone name, default `Australia/Perth`, validated with `Intl` at start (`assertZone` in `lib/dates.mjs`); an unknown name exits with a message naming the variable. `lib/dates.mjs` is the only module that names a zone: `zoneName`, `zoneDate(instant)`, `zoneMinutes(instant)`, `zoneDayStart(iso)`, `zoneDayEnd(iso)` and `zoneParts(instant)` are what everything else calls. `test/tz-guard.test.mjs` fails if another module (server, lib, scripts or public) names a zone or a fixed offset.
- Day stepping is calendar arithmetic on `YYYY-MM-DD` strings (`addDays`, `daysBetween`), never a multiple of 86,400,000 ms, so cycles, days to payday and windows are right across the Sydney changeovers (first Sunday of October forward, first Sunday of April back). Timestamps stay UTC ISO; dates stay plain text, never rewritten when the zone changes.
- The server stamps the zone into `core.js` as it serves it (`__TZ__`), and into the asset version, so the browser formats days in the server's zone, works offline from the cached shell, and drops stale caches when the zone changes.
- Two things are not driven by it: the exchange hours for ASX and US quotes (`MARKET_ZONES`, properties of the exchanges) and the public holiday list the forecast uses to pull a payday back (`waHolidays` in `lib/forecastmath.mjs`, Western Australia only; outside WA a state holiday can leave a forecast payday a day out).

## Screens

Every screen follows the maintainer's UX standards: offline-first (reads cached in localStorage, writes and receipt photos queued and flushed on reconnect), optimistic writes with rollback and the real error, 5 second undo on deletes, skeletons plus a load bar plus a slow warning, forms that keep their input, 44px targets, light haptics, reduced motion. ### Design system

Mint is phone-first (pwa + apk) and sits on the maintainer's separate UI kit, vendored into `public/kit/` and not edited by hand here (`public/kit/VERSION` is the kit commit). `public/kit/kit.css` loads first on `<html class="k-root" data-theme="dark" data-density="phone">`, then `public/style.css`, which keeps Mint's own palette, green gradient net worth hero, tracked-caps labels and glass dock, and takes the kit's face (Geist), phone type roles (body 16, secondary 14, meta 12 minimum, row title 17 at 600), toasts, sheet spring and focus-pull list entrance. `public/kit-boot.js` imports `kit.js` as `window.kit` (no inline script, the CSP is `script-src 'self'`); if it fails to load, `core.js` falls back to its own toast and plain CSS motion. Rows wrap their title and meta rather than ellipsize (only the virtualised transactions list cuts, its sheet shows the full title). Neutral `.chip` is plain text, ok, warn and bad keep their fill. Before and after shots: `docs/kit-pass-2/`. Dark only; the kit has a light theme but Mint does not ship one.

One stylesheet, `public/style.css`, and one rule: a screen takes its look from tokens and shared classes, with no literal values. Dark only (`color-scheme: dark`). Shots and the before/after of the 2026-10-20 pass are in `docs/ui-pass/`, and of the motion and polish pass that followed (Emil, Impeccable and Apple lenses) in `docs/design-pass-2/`. `node scripts/ui-shots.mjs <dir>` shoots every screen at both sizes against the fixture servers and reports horizontal scroll, targets under 44px and clipped text.

### Demo mode (Settings)

Hand the phone round without showing the real money. A switch and a Shuffle numbers button on `/settings`; stored in this browser's localStorage (`mint:demo`, `{ on, factor }`), per device, never sent to the server. While it is on the Ask tile on Home is hidden and More shows "Demo mode is on" under Settings.

- One global factor between 0.35 and 2.6, never inside 0.7 to 1.4, scales every dollar at the formatting layer, so tiles still sum to net worth and bars, percentages and chart shapes are untouched. Shuffle picks a new factor at least 15 percent away from the old one. The factor survives reloads while demo is on, is dropped when it goes off, and is never shown (it would give the real figure away). A stored value that is not a valid on-state reads as off. Form drafts are not kept while demo is on (`drafts.set` does nothing, `drafts.get` returns nothing), so a scaled figure is never restored later and a real draft never prefills a demo screen; real drafts return when demo is off.
- The pure rules (range, picking, scaling, scaling `$` amounts in server sentences, masking digits, which writes are blocked) are `public/demo-math.js`, tested in `test/demo-math.test.mjs`; it loads before `core.js`. `core.js` applies it: `money`, `money0`, `signed`, `compact`, `unitPrice` (share prices), `centsToInput` and `dollarsIn` (form prefills) all scale; `parseMoney` scales back so form checks agree with the screen; `moneyText(s)` scales dollar amounts inside a sentence the server wrote (alerts, the weekly line, tax estimate notes, payoff reasons, owed notes); `acctText(s)` masks account numbers, BSBs and last-4 digits (`xxxx4710` shows `xxxx••••`, `Income 2509` shows `Income ••••`). Merchant names and descriptions stay.
- Writes: `apiCall` in `core.js` is the one choke point; with demo on a POST, PUT, PATCH or DELETE never leaves the page, throws "Turn off demo mode to make changes" and toasts it. `mutate`, `undoable` (before anything changes on screen), `queue.push`, `queue.flush` (changes saved before demo went on wait until it is off, and a flush that demo interrupts stops like offline, keeping that change and the rest; turning demo off flushes them) and the receipt photo queue refuse too. Allowed POSTs carry nothing the page typed: `/api/rules/preview`, `/api/income/sources/preview`, `/api/budgets/starter` with `dry_run`, and `/api/sync`.
- Off in demo mode: the chat button, the Home Ask tile and chat itself (`chatUi.open` toasts "Chat is off in demo mode"; chat answers carry real dollars), amounts and recent searches in the search palette, and the CSV, tax export and accountant pack downloads (they carry real figures). The tests `test/demo-core.test.mjs` and `test/demo-guard.test.mjs` pin the formatters, the guard and a source ban on formatting currency outside `core.js`.
- Made-up balances: a zero scaled is still zero, so an empty account would look empty on a demo screen. With demo on, a cash account (effective type `transaction` or `savings`, never a loan, credit card or manual asset, and not a foreign-currency manual account) whose real balance is between $0.00 and $0.99 shows a believable made-up one: roughly $400 to $6,000 for a transaction account, $2,000 to $25,000 for savings, cents never `.00` (e.g. $2,413.60). The figure comes from a hash of the account id and the current factor (`demoFakeBalance`), so it is stable across redraws and changes on Shuffle numbers; it is worked out in real cents so the scaled figure lands in the band whatever the factor. Display only: nothing is written, no API answer changes, the write block is as before, and `accountsData` and the saved reads keep the real figures. An overdrawn account, a missing balance and anything $1 or more are left alone. Where the server sums balances into one number, the demo layer adds exactly what it made up, so the screen still adds up: `demoNetWorth` (Home net worth and the cash tile), `demoAccountsData` (the Accounts pane net worth and the account lists, balances pane, account page header and key facts, account sheet, manual account rows), `demoSavings` (the Save screen savings total and rows) and `demoGoals` (the account line on a goal card; goal progress is a goal figure and stays). `core.js` exposes them as `shownAccounts`, `shownAccount`, `shownAccountsData`, `shownNw`, `shownSavings` and `shownGoals`. Interest saved by the offset on the home loan, the loan and offset figures on Plan, transactions, charts and spend figures keep the real numbers (so the home loan card can say "on $0 in your offset" beside an offset row that shows money). Tests: `test/demo-math.test.mjs` (the rule, bands, determinism, sums) and `test/demo-core.test.mjs` (the `core.js` side and that the screens read through it).
